# Nomadic Chains

**Goal:** A Tripwire-class chain model for corps with no home hole: chains as named trees rooted at k-space entrances, an all-seeing forest view plus ad-hoc tabs (personal, or director-shared for ops), over the existing single corp map — one shared graph, occurrences layered on top.
**References:** CLAUDE.md "Mutation pathways" / "Realtime" / "Database"; `src/db/schema/ap/map_system.md`, `map_connection.md`, `map_event.md`; `src/components/map/MapCanvas.md`; `src/lib/map/mutations/systems.md`, `connections.md`; `src/lib/map/applyEvent.md`.

---

## Settled design (decided in workshopping — not up for re-litigation by an executing session)

- **Canonical data, occurrence presentation.** `ap_map_system` stays UNIQUE per (map, system); signatures, status, alias, lock, notes remain per canonical row and are therefore shared across every occurrence (a deliberate improvement over Tripwire). Chains add an *occurrence layer*: `ap_map_chain` (tab identity) + `ap_map_chain_member` (tree position). The canvas in chain mode renders one node per **membership** (`chainId:mapSystemId` xyflow ids), not per system.
- **Chains are trees, never merged.** Root = the chain's anchor (typically its k-space entrance). Parent = the member you charted/jumped from. Depth is derived, not stored.
- **Pointer-leaf on cross-links (by fiat).** A connection whose far side already belongs to a different chain (or would revisit this chain — a loop) renders as a terminal pointer-leaf ("continues in *Chain B* →" / "loops to *X*"), never a recursive unfold. Clicking a pointer-leaf switches to that chain's tab focused on the target.
- **Tabs = chains.** `kind='personal'` (any active character may create/rename/delete their own, invisible to others) and `kind='shared'` (director-created via `canManageMap`, visible to every viewer — the "temporary corp op" case). One anchor per chain. The tab strip wraps/scrolls (Wingspan runs 2+ rows).
- **Layout is generated, not manual.** One layout engine: a tab renders one tree (root top, children fanned horizontally, depth vertical); the All view renders every chain side by side at natural width, horizontally scrollable. Chains can be *wide* (Thera: ~30 children at depth 1). Zoomed out, a chain collapses to a labeled blob ("Thera · 34 systems · 5 HS exits"). Free-canvas mode is untouched; chain mode is a per-user display toggle on the map page, no schema.
- **Tracking placement:** a tracked pilot's jump creates the new membership as a child of the membership they jumped *from* (the traversed connection identifies it). Manual adds/pastes join the chain whose tab is active; with no active chain they stay chainless (rendered under an "Unassigned" pseudo-column in the All view).
- **Membership is written at charting time, not derived** — the parent relation is *how it was charted*, which an undirected graph cannot reproduce. One *real* occurrence per system per chain — a **partial** unique index `(chain_id, map_system_id) WHERE pointer_chain_id IS NULL`, because a loop pointer-leaf names a system that already occurs in the same chain and a full UNIQUE would forbid it.
- **Realtime:** chain + membership mutations are ordinary map events (new `chain.*` event kinds inside `ap_map_event` — the WS task vocabulary is untouched; this is payload, not protocol). Personal chains fan out like everything else; non-owners simply don't render them.
- **Out of scope:** auto-tag schemes per chain (0121 stays Home-rooted), multi-anchor tabs (rejected), any change to the mutation pathways or WS task vocabulary.

## Stage 3 — Forest layout engine + LOD spec
**Mode:** Execute
**Status:** done — a86bcf6
**Goal:** A pure, tested layout module: memberships in → positioned occurrence nodes + edges out, for one tree or the whole forest, plus the blob-collapse decision function.
**References:** this stage's spec below (the design is settled — do not re-derive it); Stage 1's `ap_map_chain_member` shape; `src/components/map/MapCanvas.md` only for the consuming render path's expectations (Stage 4).
**Touches:** new `src/lib/map/chains/layout.ts`, `src/lib/map/chains/collapse.ts` (+ companions), `tests/unit/chain-layout.test.ts` (+ companion). Pure modules — no components, no schema, no API.

**Spec (designed 2026-08-27):**
- **Tree layout** — hand-rolled recursive tidy-tree, no new dependency: a subtree's breadth is `max(nodeW, Σ children breadths + gaps)`, parent centered over its children's span, depth axis = `depth × (nodeH + gapY)`. O(n) over members. Children order deterministically by member id (creation order) so growth never shuffles siblings. Pointer-leaves lay out as fixed-size leaf pills. Node/gap dimensions are parameters (`{ nodeW, nodeH, gapX, gapY }`) — the module never imports UI constants.
- **Orientation** — computed in logical (breadth × depth) coordinates, transposed at the end: `root-top` (depth grows downward) or `root-left` (depth grows rightward). A per-user display preference (client-persisted with the map-layout prefs; no schema).
- **Forest packing** (All view) — each chain is a bounding block; shelf-packed into rows wrapping at a supplied viewport width (row height = tallest block in the row). Order: shared chains, then personal, each by creation order; the "Unassigned" pseudo-chain (chainless systems as a plain grid block) last. Order never keys on size, so growth doesn't teleport chains. Re-flow on resize is accepted.
- **Collapse decision** (`collapse.ts`) — pure function of `{ systemCount, zoom, threshold, expandedOverride }` with defined precedence: below the zoom cutoff (constant, ~0.35) every chain is a blob; above it, a chain blobs when `systemCount > threshold` unless the session-local expansion override is set. `threshold` is the viewer's `ap_user.chain_blob_threshold` (default 15 — Tripwire's default).
- **Blob content contract** (consumed by Stage 5's renderer): chain name, system count, k-space exit summary grouped by security class (e.g. "34 systems · 5 HS · 2 LS"), and presence of rally / EOL-critical flags. Hit behavior: click selects (chain summary in the sidebar), the expand affordance toggles the session override, double-click opens the chain's tab.
- **K-space roots and exits render visually distinct** from J-space occurrence tiles (the Tripwire oval-vs-rectangle legibility goal; Stage 4 picks the treatment).
- **Chain mode is not draggable** — the generated layout owns positions; manual drag belongs to the free-canvas mode only.
**Done when:** unit tests cover subtree-breadth math, sibling stability under an added child, both orientations agreeing under transpose, shelf-wrap at a given width, pointer-leaf sizing, and every collapse-precedence branch; `pnpm typecheck && pnpm lint && pnpm test` green. No UI is rendered by this stage.

## Stage 7 — Chains-near-me
**Mode:** Execute
**Status:** done — a85b710
**Goal:** Every chain answers "how far is this from me" — the orientation feature Tripwire lacks (Chase Boirelle: "difficult to interpret… where any of them are in relation to you").
**References:** `src/lib/map/gateGraph.md` (`bfs`, adjacency), `src/lib/map/routePlanner.md` (`getGateGraph` — memoized adjacency; do not reload the edge table), `src/components/map/MapPresenceContext.md` (live pilot locations), Stage 4's tab strip (`src/components/map/ChainTabStrip.tsx` — presentational; props are `{ chains, activeChainId, canManage, orientation, onSelect, onOrientationChange, onCreate, onRename, onDelete }`, each tab renders kind icon + name, so the `Nj` badge is a new per-tab element fed by a new prop, e.g. `distances: Record<chainId, number | null>`) and Stage 5's blob renderer (consumers).
**Touches:** new `src/lib/map/chains/distance.ts` (+ `.md`), new API route `src/app/api/map/[mapId]/chain-distances/route.ts` (+ `.md`), tab-strip + blob + chain-summary rendering touches, a unit test for the distance reducer.

**Spec (designed 2026-08-27):**
- **Semantics.** Distance is **gate jumps, shortest, unweighted** — orientation, not navigation (the route module owns safety-weighted actual routing). For each chain: `min` over its k-space member systems ("exits") of BFS distance from the viewer's origin set. Chains with no k-space member show "—" (unreachable by gates), never 0.
- **Origin set.** The viewer's tracked pilot location (route-source picker precedent: the selected/first active character with a known location). In k-space: the origin is that system. In J-space: the origin set is the k-space exits of whichever chain contains the pilot's current system (min over pairs); if no chain contains it, distances are unknown and the badges hide. This "from inside my chain" case is the everyday WDS case and must work.
- **Compute.** Server-side: one multi-source BFS over `getGateGraph().adjacency` (seed the queue with every origin at distance 0), then min per chain over its exits — O(V+E) once per request, ~8.5k systems, no per-chain BFS. `GET /api/map/[mapId]/chain-distances` (view-gated) returns `{ characterId, originSystemId | null, distances: Record<chainId, number | null>, nearestExits: Record<chainId, solarId | null> }` for every chain the viewer can see (personal = own only, shared = all).
- **Freshness.** Client refetches on panel/tab-strip mount and debounced on the viewer's own presence `characterUpdate` (location change); no realtime channel of its own, no server cache beyond the memoized gate graph.
- **Surfaces.** A small `Nj` badge on each chain tab (tooltip: "N jumps to <exit system> via gates"), the same figure in the Stage 5 blob (`ChainBlobNode` in `src/components/map/ChainBlobNode.tsx` — render the badge beside the `formatChainBlobLine` summary; `ChainBlobContent` itself stays distance-free, it is derived per render) and the chain-summary sidebar (`ChainInspector` in `src/components/sidebar/InspectorModule.tsx` — the surface a blob click opens, via `SelectionRef` kind `'chain'`). No sorting by distance (tab order stays stable — the Stage 3 invariant).
**Done when:** unit test covers the reducer (min-over-exits, J-space origin-set case, no-exit chain → null); with two chains seeded, the endpoint returns hand-checkable jump counts (Jita → Perimeter = 1 fixture idiom from `universe-ingest`); checks green. (Badge render/hide with no located pilot is a browser check — moved to `## Manual verification`, Stage 7; the endpoint's unknown-response side is integration-tested.)

- **Stage 2b** — `attachChainMemberOnConnection`'s tree-adjacent via backfill stamped the *far* member unconditionally; on a child→parent traversal that's the parent (even a root, whose via must stay null), violating the shuttle-writes-nothing constraint on the first return jump. It now backfills the child of the adjacent pair, whichever endpoint that is.
- **Stage 2b** — fan-out authority decision: a tracked jump grows shared chains plus the jumping pilot's **own** personal chains; foreign personal chains are excluded (consistent with the write-path guard, which throws "Chain not found." for them). When several chains hold the from-system, attaches run in chain-id order per-chain-transaction — the earliest chain accretes the real occurrence of the destination and later ones accrete pointer-leaves to it (the attach helper's already-chained rule), stable across retries.
- **Stage 3** — the layout params are logical (breadth × depth), not screen, extents: `nodeW`/`gapX` run along the breadth axis, `nodeH`/`gapY` along depth, and the whole plane is transposed at the end — so under `root-left` a tile renders `nodeH` wide × `nodeW` tall, and depth spacing is always `nodeH + gapY`. Stage 4/8a pass params in these logical terms (don't pre-swap them per orientation).
- **Stage 3** — the four-param `{ nodeW, nodeH, gapX, gapY }` contract gained optional `pointerW`/`pointerH` (defaulting to the tile size) so pointer-leaf pills stay parameter-driven instead of importing a UI constant — the only way "fixed-size leaf pills" can size differently from tiles without the module knowing UI dimensions.
- **Stage 3** — a chain with zero members lays out as a 0×0 block in `layoutForest` (it consumes no shelf space); Stage 5 owns whatever placeholder presentation an empty chain gets. Defensive shapes: a member whose parent is missing from the set becomes an extra root (roots lay side by side inside the chain block); members trapped in a parent cycle are omitted.

- **Stage 4** — id-scheme refinement: the settled `chainId:mapSystemId` occurrence ids cannot cover *loop* pointer-leaves (the target system already really occurs in the chain — the partial unique index exists for exactly this), so pointer pills key `chainptr:<memberId>`. Tree edges use the **live backing connection id** as the xyflow edge id (edge click/selection then drives the canonical connection inspector unchanged), with `chainedge:<childMemberId>` for collapsed/unknown vias; within one chain a connection backs at most one link, so the id is unique.
- **Stage 4** — the client's personal-chain ownership filter must use the **session character id** (new `sessionCharacterId` prop on `MapCanvas`, from `session.characterId`), not the account roster: `loadMapForView` filters by the login character, so filtering by all account characters would make an alt-owned personal chain appear mid-session (realtime fans every chain out) and vanish on reload.
- **Stage 4** — the free-canvas ReactFlow *unmounts* while a chain tab is open, so its captured `flowInstance` goes stale: `onJumpToSystem` / sig-search centering branch through a `ChainFocusRequest` in chain mode, and `lastViewportRef` (fed by `onMoveEnd`) restores the free viewport on remount. `MapHotkeys` arrow-move still reads stale free-canvas positions in chain mode — selection-only, non-crashing, left as-is.
- **Stage 4** — a locally-drawn connection's `chain.member.added` reaches the drawer over realtime only (Stage 2's response-shape decision), so the new child/pointer appears with realtime latency rather than in the POST fold — no canvas special-casing needed, but don't mistake it for a bug when testing on a laggy socket.
- **Stage 4** — chain-mode manual add parents on the selected occurrence's member, else the chain's root (an empty chain makes the add its root) — `attachChainMemberOnSystemAdd` refuses a second root, so the root fallback is what makes "add with nothing selected" work on a non-empty chain.
- **Stage 5** — the Stage 4 "edge id = live connection id" convention cannot survive the forest: one connection can back links in **several chains at once** (a shared and a personal chain tracking the same route), and xyflow edge ids must be unique — so forest edges are all `chainedge:<memberId>`, with canonical selection/context-menu resolved from the connection carried in the edge data (the endpoint-menu callback closes over the connection id per edge, since `ConnectionEdge` passes its own edge id). Consequence: the travel-pulse animation (keyed on edge id) doesn't play on forest edges. Single-chain tabs keep the Stage 4 convention unchanged.
- **Stage 5** — forest geometry is computed from **full tree footprints only** (`layoutForest` gained an optional `blockGap` for wider inter-chain spacing): collapse swaps what renders inside a block but never re-packs the shelf, so crossing the zoom cutoff or toggling expansion can't teleport blocks mid-gesture. The live zoom feeds React state only when it crosses `CHAIN_BLOB_ZOOM_CUTOFF` (the boolean is the only thing the collapse decision reads), so pan/zoom never rebuilds the node arrays otherwise.
- **Stage 5** — ReactFlow's default `minZoom` (0.5) sits **above** the 0.35 blob cutoff — the blob-by-zoom LOD would be unreachable and a WDS-scale forest couldn't fit; `ChainForestCanvas` sets `minZoom={0.05}`. `ChainCanvas` (single tab) keeps the default deliberately.
- **Stage 5** — an empty chain renders nothing in the All view (no blob, no caption — its tab is the affordance), resolving the Stage 3 note's open placeholder question. `SelectionRef` gained kind `'chain'` (blob/caption click → read-only `ChainInspector` summary; every other `selected` consumer treats the new kind as no-selection naturally). K-space exit display classes map `H`→`HS`, `L`→`LS`, `0.0`→`NS`, others raw (`P`, `A`).
- **Stage 6** — `MAX_SYSTEMS_PER_MAP` has **no code consumer**: nothing enforces the ceiling at add-time (the companion's "applied where visible = true" describes intent, not code). Raising 400→1500 is therefore declarative; the measurements below are the substantive deliverable. Recorded so nobody hunts for the enforcement site.
- **Stage 6** — DB-seeded fixture is the **permanent** `scripts/seed-scale-fixture.ts` (+`pnpm seed:scale-fixture`), not a throwaway: the Stage 5 pan-smoothness and Stage 8a phone checks want the same 1000-system map in a real browser. - **Stage 6** — **loadMapForView at WDS scale: median 186 ms** (10 runs: min 167, max 280) — measured from the dev Mac against a throwaway `aperture-postgres:dev` container on nautilus through an SSH tunnel; measured `SELECT 1` RTT was ~6.8 ms and the load path runs ~10 sequential queries, so ≈68 ms of the median is tunnel latency (server-side ≈120 ms). ~16× inside the 3 s bound even uncorrected. Serialized `MapViewData` is **2.44 MB** (4960 signatures dominate) — fine self-hosted, but the number to watch if per-system sig counts grow.
- **Stage 6** — chain.* payload audit vs the 8 KB `pg_notify` ceiling: all four kinds are fixed per-event scalars. Worst case (19-digit ids, 40-char names at 3-byte UTF-8, optional fields present): `chain.created` 339 B, `chain.renamed` 241 B, `chain.deleted` 202 B, `chain.member.added` 540 B. Nothing scales with map size — the bulk prunes (chain delete's member cascade, system removal's every-chain prune) emit no per-member events by the Stage 2 design, so no chain payload can grow with the cap.
- **Stage 6** — bulk-flow math at 1500: signature paste is per-system (scanner-bounded, cap-independent); housekeeping deletes batch at `JOB_DELETE_BATCH_SIZE` 500/run (cap-independent); import bounds (2000 systems / 4000 connections / 8000 signatures) still fit a full 1500-system export, though a map averaging >5.3 sigs/system now exceeds the 8000-sig import bound (clean Zod 400, no partial write — was already reachable at 400×20). One flow did **not** batch: `fetchSystemData` sent the whole on-map id set to `/system-data` (route 400s over 256 ids), so the 5-minute whole-map intel/stats refresh silently failed on any map >256 systems — pre-existing at the 400 cap, fatal at 1500. Fixed client-side: `fetchSystemData` now chunks into ≤256-id parallel requests and merges (6 requests per refresh at 1500). Subchain/disconnected teardown stays one transaction of N tiny events (~3000 notifications worst-case at the new cap — well inside Postgres's notification queue).
